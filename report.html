3. 系统架构

三层职责清晰：前端只负责交互与渲染；app.py 处理 HTTP、会话、统计、管理接口；rag_core.py 是把 RAG 所有“硬逻辑”（检索、重排、改写、生成、降级、归一化）收敛成的共享核心，被服务直接复用。

4. 一次问答的数据流

用户提问→ 智能改写(可选)→ 向量检索 + 关键词重排→ 拼上下文→ LLM 流式生成→ 前端渲染 + 来源卡片
  1. 改写：若开启“智能检索”，先用 LLM 把口语化问题改写成更适合检索的查询（如“无锡本科能投的数据开发实习” → 强调“无锡/数据开发/实习/本科”）。
  2. 检索：对查询做 bge-m3 嵌入，在 Chroma 取向量近邻；同时用中文 bigram 提取关键词做字面匹配，两者分数经 RRF 融合重排，取 top-5。
  3. 拼上下文：把 top-5 岗位的结构化字段拼成检索上下文，连同对话历史交给 LLM。
  4. 生成：LLM 逐 token 返回，后端用 SSE 推给前端，前端实时渲染并展示参考岗位卡片。
  5. 兜底：若生成失败（限流/超时），自动降级为“列出检索到的岗位”，保证永远有结果。

5. 关键实现原理

5.1 嵌入与向量库

使用 BAAI/bge-m3 多语言嵌入模型（经硅基流动 API 调用），把每条岗位的“标题+城市+类型+要求+标签”文本映射为向量，存入 Chroma 持久化目录 chroma_db/。查询时实时嵌入，与库中向量做余弦相似度检索。查询嵌入结果做了 LRU 内存缓存，相同/相似问题不必重复调用 API。

5.2 混合检索（核心召回策略）

纯向量检索容易漏掉“字面强相关但语义近似度不高”的岗位。本系统叠加一路中文 bigram 关键词匹配，并用 RRF（Reciprocal Rank Fusion） 把两路排序融合：

# 伪代码
vec_scores = chroma.query(embed(q), top_k=12)
kw_scores  = bigram_match(q, corpus)        # 中文二元文法字面匹配
fused      = rrf(vec_scores) + rrf(kw_scores)
return top5(fused)

这显著提升了“无锡+数据开发+实习”这类强约束 query 的命中率。

5.3 智能检索：LLM 查询改写

用户口语（如“我想找点无锡那边数据相关的活”）经 rewrite_query 调用 DeepSeek 改写为结构化检索式，再进入检索链路，召回更准。

5.4 流式生成（SSE）

后端用 Flask 的流式响应，按 data: {type:"token", token:"…"} 逐片推送；前端边收边用轻量 Markdown 渲染，呈现“打字机”效果，并先推 sources 事件渲染来源卡片，最后推 done。

5.5 稳定性设计

  • 抗限流：make_client 构造带 timeout 与 max_retries 的指数退避客户端。
  • 句柄自愈：索引重建期间旧 Collection 句柄会失效，_safe_col 在每次访问时校验并自动重连，避免 500。
  • 重建锁：/rebuild 加进程锁，防止并发重建导致索引损坏。
  • 降级：生成失败时回退到“列出检索岗位”，用户始终拿到资料。

5.6 数据归一化

原始数据城市字段常有“无锡新吴”“全国(含上海)”等脏写法。normalize_city 按核心城市列表做子串优先匹配；normalize_edu 把“本科/硕士/博士”等区间映射到统一层级；统计时其余城市归并“其他”，保证看板干净。

5.7 数据扩充（并发采集）

collect_jobs.py 用 DeepSeek 基于真实岗位分布 + 广度种子公司批量生成结构化岗位，6 路并发 API 调用，去重校验后写入 jobs.json 并标注 source="ai-augmented"，约 9 分钟从 1100 扩到 2000 条。
